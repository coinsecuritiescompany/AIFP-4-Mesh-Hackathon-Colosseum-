# Delivery journal storage boundary

Each node opens its own `mesh-delivery.sqlite` in its private data directory. The journal uses Node's built-in SQLite API, WAL mode and synchronous FULL. The node writes a newly created outgoing delivery to SQLite before calling a transport. Incoming delivery records are also written before the journal method returns. Batch delivery completion uses one transaction. A failed database write leaves the journal's in-memory view unchanged.

On first startup with an existing `mesh-state.json`, the journal imports the old `deliveryOutbox`, `deliveryInbox` and replay `seen` entries and records migration markers. Later restarts use the database as the authority even if an old JSON snapshot remains. The Ed25519 and libp2p key files keep their existing paths and bytes. The JSON state writer no longer includes those imported journal and replay maps. Receiving a signed envelope inserts the replay marker and incoming journal entry in one transaction; a failed journal write rolls both back.

Active Mesh forwarding now stores logical bundles and hop records in each node's SQLite WAL database. Inbound acceptance atomically inserts the complete bundle, replay marker and inbox record before the node creates a signed `HOP_ACCEPTED`. Hop states and bundle states enforce checked transitions. A late ACK can match a recently retried message ID. The legacy journal and JSON relay queue are retained for migration; the active coordinator reads its SQLite tables. Payment execution, peer state, identities and partial TCP fragments still reside in separate files. There is no atomic transaction across financial execution and Mesh custody. `node:sqlite` is provided by the project's Node runtime. Back up the entire node data directory as a unit; never share a live database between nodes.
