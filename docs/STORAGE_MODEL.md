# Delivery journal storage boundary

Each node opens its own `mesh-delivery.sqlite` in its private data directory. The journal uses Node's built-in SQLite API, WAL mode and synchronous FULL. The node writes a newly created outgoing delivery to SQLite before calling a transport. Incoming delivery records are also written before the journal method returns. Batch delivery completion uses one transaction. A failed database write leaves the journal's in-memory view unchanged.

On first startup with an existing `mesh-state.json`, the journal imports the old `deliveryOutbox` and `deliveryInbox` entries in a transaction and records a migration marker. Later restarts use the database as the authority even if an old JSON snapshot remains. The Ed25519 and libp2p key files keep their existing paths and bytes. The JSON state writer no longer includes the two imported journal maps.

This is an incremental storage migration. Peer state, replay state, relay queue, receipts, payment records and partial TCP fragments still reside in their existing files. There is no atomic transaction between those files and the SQLite journal. In particular, an inbound journal record alone is **not** proof that a relay took durable custody of the bundle; a signed asynchronous hop acceptance protocol must wait until the relay payload and replay state are committed together. The existing `ACKNOWLEDGED` state still comes from a synchronous peer response. It must not be described as delayed hop acceptance.

SQLite is local to each process; copying a database between live nodes is unsupported. Keep the node's entire data directory together when backing up or restoring identities and state. This initial migration uses `node:sqlite` available on the project's Node 22 runtime; the upstream API is still marked experimental.
