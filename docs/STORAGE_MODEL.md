# Delivery journal storage boundary

Each node opens its own `mesh-delivery.sqlite` in its private data directory. The journal uses Node's built-in SQLite API, WAL mode and synchronous FULL. The node writes a newly created outgoing delivery to SQLite before calling a transport. Incoming delivery records are also written before the journal method returns. Batch delivery completion uses one transaction. A failed database write leaves the journal's in-memory view unchanged.

On first startup with an existing `mesh-state.json`, the journal imports the old `deliveryOutbox`, `deliveryInbox` and replay `seen` entries and records migration markers. Later restarts use the database as the authority even if an old JSON snapshot remains. The Ed25519 and libp2p key files keep their existing paths and bytes. The JSON state writer no longer includes those imported journal and replay maps. Receiving a signed envelope inserts the replay marker and incoming journal entry in one transaction; a failed journal write rolls both back.

This is an incremental storage migration. Peer state, relay queue, receipts, payment records and partial TCP fragments still reside in their existing files. There is no atomic transaction between those files and the SQLite journal. In particular, an inbound journal record alone is **not** proof that a relay took durable custody of the bundle; a signed asynchronous hop acceptance protocol must wait until the relay payload is committed as well. The existing `ACKNOWLEDGED` state still comes from a synchronous peer response. It must not be described as delayed hop acceptance.

SQLite is local to each process; copying a database between live nodes is unsupported. Keep the node's entire data directory together when backing up or restoring identities and state. This initial migration uses `node:sqlite` available on the project's Node 22 runtime; the upstream API is still marked experimental.

The next schema adds `mesh_bundles` and `mesh_hops`. A newly queued logical bundle and its selected hop can be inserted in a single transaction before sending; inbound replay ID, inbox entry and the complete bundle can also be inserted atomically. Bundle hashes bind the stored payload, and admission checks enforce an item, total queue and per-origin limit. Persisted state transitions reject stale or backwards updates. These primitives are covered by crash/reopen tests, but the active `MeshNode` payment path does not yet use them. No signed custody acknowledgement is issued by this schema change alone.
