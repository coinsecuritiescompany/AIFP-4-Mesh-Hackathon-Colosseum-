# Disruption-tolerant behavior

The origin writes the intent to its own payment store before forwarding. Without a path, it records `queued_for_mesh`. A periodic tick exchanges advertisements and retries queued intents when the graph changes. Expiry is checked before dispatch and at the receiving node. The queue survives process/container restart in a per-node Docker volume. Message replay IDs, advertisements, node keys and signed receipts are also persisted locally.

Relays also persist accepted payment bundles when the next hop cannot be reached. They acknowledge custody to the previous hop, retry with bounded exponential backoff, and discard expired bundles. The settlement node can forward a signed receipt asynchronously toward the origin; relays persist receipts if the return path disappears. Every hop signs a fresh short-lived envelope, while the original payment signature remains unchanged. An expired route advertisement inside a previously accepted bundle does not invalidate the still-valid signed payment intent. The integration test restarts a relay holding a bundle and verifies subsequent delivery and one settlement.

This borrows store-and-forward, lifetime and convergence-adapter ideas from BPv7. It is **not a BPv7 bundle agent**: it does not emit RFC 9171 primary/canonical blocks, use BP endpoint IDs, implement custody/administrative records, BPSec, or interoperate with TCPCLv4. There is no standardized custody transfer, fragmentation/reassembly, or cross-implementation interoperability. Per-relay queues are bounded by available local disk, not by a configured quota. These gaps must be resolved before deployment on constrained/untrusted networks.

If C's settlement outcome is unknown, C leaves the intent `executing`; the origin must not blindly retry a different rail. A lost receipt can be recovered through a repeated intent because C returns its persistent settled receipt, but automatic uncertainty resolution against Solana RPC remains future work.
