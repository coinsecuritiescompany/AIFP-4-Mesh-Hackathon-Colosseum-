# Crash recovery boundaries

Each node persists outgoing Mesh bundles and hop records before transport submission. Inbound complete bundles, inbox entries and replay markers commit together in SQLite WAL. Unaccepted hops retry with a fresh signed wire ID after restart; `HOP_ACCEPTED` can arrive for a previous submission of the same hop. A relay keeps the original signed payment unchanged. Partial TCP and libp2p reassembly persists in separate bounded files. Missing frames still require retransmission of the whole envelope.

The settlement node records its execution state before calling a rail. An uncertain external result remains `executing` and must be reconciled instead of blindly retried. If a crash happens after the signed Mesh receipt is saved but before its outbound bundle is queued, the still-queued inbound payment causes the coordinator to recreate that receipt bundle on restart. The origin verifies the receipt first, then persists intent state, receipt and transaction in one atomic JSON file replacement. Duplicate receipts cannot create another local transaction.

Financial payment storage and the Mesh SQLite journal are separate local stores. No cross-store transaction exists. A node may retry delivery at least once; the persistent settlement record and provider idempotency key must prevent a second external execution. This is a local MVP crash model, not a distributed consensus guarantee. A production deployment needs transactional settlement records, provider status reconciliation, monitoring and backup/restore procedures for the complete per-node data directory.
